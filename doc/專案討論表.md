# 餐飲地圖系統 - 三週專案討論表

> 目的：協助五人小組在「前置作業完成後」用三週正式製作時間完成可 Demo 的 ASP.NET MVC 餐飲地圖系統。  
> 分工原則：一個人負責一個功能頁或功能模組，包含前端、後端、資料庫串接、JavaScript 與基本測試。
> 使用方式：開會時逐項討論「待討論 / 組員意見 / 最終決議 / 負責人 / 期限」，由組長彙整後拍板。

## 12. 風險與備案表

| 風險 | 可能影響 | 預防方式 | 備案 | 負責人 |
|---|---|---|---|---|
| 初學者看不懂 AI 產生的程式 | 後續無法除錯或報告時講不清楚 | 每個功能負責人要能口頭解釋自己的流程 | 組長安排短講解與 code review |  |
| Google Maps API Key 申請或設定失敗 | 地圖功能無法 Demo | 第一週 Day 2 前確認是否可用 | 改用 Leaflet + OpenStreetMap，或先只保留地址與距離排序 |  |
| 地圖搜尋太花時間 | 影響評論、收藏等核心功能 | 地圖先做標記與彈窗，距離排序列 Could | 只展示餐廳標記與清單 |  |
| 圖片上傳卡關 | 餐廳新增功能延遲 | 先用圖片 URL 或種子資料 | 第三週再補上傳 |  |
| 會員權限複雜 | 無法判斷誰能新增、編輯或互動 | 權限規則先簡化 | 先釐清登入 / 未登入差異，避免做複雜角色 |  |
| EF Core Migration 衝突 | 資料庫無法同步 | Migration 由固定一人管理 | 重新建立本機資料庫並用 Seed 資料 |  |
| Git 衝突 | 進度被卡住 | 分工避開同一檔案、頻繁 pull | 先停止 push，通知組長，由組長協助解衝突 |  |
| UI 花太多時間 | 功能做不完 | 使用 Bootstrap 元件，不自刻太多樣式 | 第三週只做一致化與基本 RWD |  |
| 功能頁彼此依賴太高 | 有人卡住會影響其他人 | 先定好資料表欄位與 Controller 回傳資料 | 用假資料或 Seed 資料先開發 |  |
| 進度落後 | Demo 不完整 | 每週末內部 Demo 檢查 | 砍 Later / Could，只保 Must |  |
